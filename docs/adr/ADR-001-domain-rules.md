## 0. 背景与冲突来源

现有三份材料对同一规则给出了不一致的答案，实现里还存在第三套口径。本 ADR 逐项冻结，冲突裁决原则按《迭代开发计划》第 3 节与任务单默认原则执行：

1. **心情必选一个。**
2. **GP 属于空间**，植物只是空间当前的成长载体。
3. **删除记录后重新计算** GP、植物阶段和成就。
4. **每日 GP 上限按「记录发生日期 + 空间」计算。**
5. **补记占用补记日期额度，不占今天额度。**
6. **共享空间只有作者可以编辑或删除自己的记录。**
7. **正式版本不自动插入 Demo 记录。**
8. **客户端可以乐观计算 GP，但未来以服务端结果为权威。**
9. **植物解锁必须支持 GP、连续天数、记录数量、地点数量、共享事件等不同条件类型。**
10. 文档冲突时，GP 公式**以 PRD 3.2.1 为基线**（迭代计划 3.2 明确建议）。

## D1. GP 计算公式（冻结）

### 1.1 公式

```
内容小计 subtotal = 基础值 + 内容丰富度加成（全部为整数加分项）
连续系数        s = min(1 + N × 0.05, 2.0)        // N 见 D2；连续第 20 天恰好 ×2
补记系数        b = occurredDate ≠ 创建当日 ? 0.8 : 1.0   // 见 D4
事件加分        e = 纪念日 +20 / 节日 +10 / 合种共振 +15（互斥于彼此？否，可叠加；见 1.4）

原始 GP   raw = floor(floor(subtotal × s) × b)
单条 GP   gp  = min(raw + e, remainingQuota(spaceId, occurredDate))
remainingQuota = 100 − 该空间该发生日所有未删除记录的 gpFinal 之和（≥ 0）
```

### 1.2 冻结的数值常量（实现唯一来源，禁止散落魔法数字）

| 常量 | 值 | 说明 |
|---|---|---|
| BASE_GP | 10 | 任意一条有效记录 |
| TEXT_BONUS | +5 | 有文字（非空白） |
| TEXT_LONG_BONUS | +5 | 文字 > 50 字（两档合计 +10，无 20/200 字档） |
| PHOTO_BONUS_PER | +3 / 张 | 最多 9 张 → +27 |
| VOICE_BONUS | +5 | 有录音 |
| MUSIC_BONUS | +5 | 有音乐 |
| LINK_BONUS | +5 | 有链接 |
| LOCATION_BONUS | +3 | 有地点 |
| STATUS_TAG_BONUS_PER | +2 / 个 | 最多 3 个 → +6 |
| MOOD_BONUS | **0** | 心情是发布前置条件（D12/R4），不是加分项 |
| STREAK_RATE | 0.05 / 天 | 系数 1 + N×0.05，上限 2.0（第 20 天封顶） |
| BACKDATE_MULTIPLIER | 0.8 | 见 D4 |
| EVENT_ANNIVERSARY / EVENT_FESTIVAL / EVENT_RESONANCE | +20 / +10 / +15 | 见 1.4 |
| DAILY_GP_LIMIT | 100 | 见 D3 |
| 取整规则 | 向下取整 | 每一步乘法后立即 `floor`，先连续系数后补记系数 |

单条理论上限（PRD 口径）：10+10+27+5+5+5+3+6 = 71，×2.0 = 142，×0.8 = 113 → 最终受当日剩余额度封顶；「一条丰富记录约 50–70」与 PRD 描述一致。

### 1.3 与现有 `GPCalculator` 的差异（Z1-03 重写清单）

| 项 | 现实现 | 冻结值 |
|---|---|---|
| 照片 | +8/张（+72 封顶） | +3/张（+27 封顶） |
| 文字 | 20/50/200 字三档 10/15/20 | 两档 +5 / +10 |
| 语音 | +8 | +5 |
| 地点 | +5 | +3 |
| 心情 | +3 | +0（必选前置） |
| 连续系数 | `1 + min(streak/7, 1)`（7 天翻倍） | `1 + N×0.05`，20 天翻倍 |
| 补记判断 | `createdAt < 今日零点`（`isBackdated(createdAt)`） | `occurredDate ≠ 创建当日`（D4） |
| 每日额度 | 按 `createdAt` 的「今天」 | 按 (spaceId, occurredDate)（D3） |

### 1.4 特殊事件加成

- **纪念日 +20**：空间内预设的纪念日当天记录；v1 离线版暂无纪念日实体，**预留参数不实现**（M5）。
- **节日 +10**：设备日历命中内置节日表当天；数据表由客户端内置（版本化），**I2 起实现**。
- **合种共振 +15**：共享空间同一发生日已有其他成员记录时，当日该空间第二位及之后的作者首条记录 +15；**幂等键 = (spaceId, occurredDate, authorId)，每人每日最多触发一次**；v1 单人版不触发（M5 实现）。
- 事件加分参与当日 100 上限封顶（默认；待确认问题 Q10）。
- 服务端为权威：客户端乐观计算展示，同步后以服务端返回的 `gpFinal` 校准（D10）。

## D2. 连续记录天数（streak）

1. **口径**：连续「有记录的自然日」天数，按**空间**统计（共享空间中任一成员的记录都算该空间有记录）；同日多条只算 1 天。
2. **日期口径**：记录的**发生日** `occurredDate`（本地时区 `LocalDate`），不是 `createdAt`、不是 UTC 日。
3. **起点宽限（保留现行为）**：今天有记录从今天起算；今天没有但昨天有，从昨天起算（容忍「睡前未记录、次日早上补看」）；两天都没有 → streak = 0。
4. **推导式而非事件式**：streak 永远从当前未删除记录集合按 `occurredDateKey` 去重后推导。因此**补记过去某天可以接上断裂的 streak**（含补记当天本身），删除记录也会使其缩短——这是「记录集合推导」的自然结果，不做事件回放修正。
5. **连续系数中的 N**：N = **含本次记录发生日在内**的连续天数（第一条记录 N=1 → ×1.05；连续第 20 天 N=20 → ×2.0），与 PRD「连续 20 天翻倍」表述一致。
6. **DST / 跨午夜**：日界以 `LocalDate`（java.time，默认时区）计算；禁止 `timestamp − 24×3600×1000` 逐天回退（DST 偏移日会错位，现实现 `StreakCalculator.kt:47` 即此写法）。实现应一次查询 `DISTINCT occurredDateKey` 后在内存逐日比较。
7. **上限**：逻辑上不封顶；「记录日数」类统计（竹林解锁）用同一 `occurredDateKey` 去重口径（修复 R6）。
8. **展示**：「需要关爱」状态 = 最近一个有记录的日子早于昨天；纯视觉，不影响 GP（植物不枯萎）。

## D3. 每日 GP 上限：日期与空间口径

1. **额度键 = (spaceId, occurredDate)**；每日上限 `DAILY_GP_LIMIT = 100`。
2. **occurredDate = 记录发生日**（本地时区日历日）。补记占用**补记日**额度，不占今天（默认原则 5）。
3. **共享空间**：100 GP/日为该空间全体成员合计（GP 属于空间的直接推论；防刷分由空间级控制）。见待确认 Q1。
4. **封顶行为**：新记录（含编辑后重算、补记）的 `gpFinal = min(raw + e, remainingQuota)`；`remainingQuota < 0` 时记 0。被上限截断的事实以 `isCapped` 持久化，用于 UI 提示。
5. **额度查询**：`SUM(gpFinal) WHERE spaceId=? AND occurredDateKey=? AND deletedAt IS NULL`；v2 以 `daily_space_stats` 缓存表加速（room-v2-schema §2.6）。
6. 合种共振 +15 计入当日额度（Q10）。

## D4. 补记（backfill）规则

1. **时间窗**：`occurredAt` 可选过去时间，最早 = 今天 − 365 天（PRD 3.1.3）；不允许未来时间。
2. **额度**：占**补记发生日**的 (spaceId, occurredDate) 额度，不占今天（D3）。
3. **衰减**：`occurredDate ≠ 记录创建当日` → 整单（含连续系数已乘部分与事件加分前的 raw）×0.8；只衰减一次，与连续系数叠乘时**先连续后补记、每步取整**（D1.1）。创建当日当天内修改发生时间为更早时刻不触发衰减（按日不按时刻）。
4. **streak**：补记写入后 streak 按记录集合重推（D2.4），补记可以接续断裂的连续天数。
5. **判定位**：`isBackdated` 为**持久化派生列** = `occurredDateKey != createdAt 的日期键`，禁止再用「createdAt 是否小于今日零点」推断（修复 R5）。
6. 编辑把当日记录改成补记（或反之）：按新发生日重算 GP 与两日额度（D5）。

## D5. 编辑记录后是否重算 GP：**重算**

1. 编辑内容（文字/媒体/标签）或 `occurredAt` 后，**该条 GP 按当前内容重新计算**，并按目标发生日的剩余额度封顶（剩余额度 = 该日**其他**未删除记录的 gpFinal 之和扣除后）。
2. 级联重算（同一 Room 事务内，Z1-02）：当日额度缓存 → space.totalGp → 植物阶段（含快照事件）→ 成就进度与解锁 → 植物解锁条件。
3. **不追溯**：同日其他记录的 GP 不因本条编辑而重新分配额度；顺序按「先发布先占额」保持确定性。
4. **编辑窗口**：PRD「发布后 24 小时内可编辑」属于同步/防作弊约束；**v1 离线版不限制编辑窗口**，24 小时限制由服务端版本执行（待确认 Q3）。
5. 编辑产生 `updatedAt`、`version+1`、syncState=SYNC_PENDING，进 Outbox（D10）。

## D6. 删除记录后如何回退 GP、植物阶段和成就

1. **软删除**：置 `deletedAt`，记录保留为墓碑（同步用）；所有统计查询排除 `deletedAt IS NOT NULL` 的行。
2. **GP 回退**：space.totalGp 重算（= 未删除记录 gpFinal 之和），当日额度缓存同步重算。
3. **植物阶段回退**：阶段由 space.totalGp 派生，GP 回退后阶段**可以降级**，写入一条 `STAGE_DOWN` 快照事件。「植物不会枯萎」指**不记录不降级**（D2.8），删除是用户主动移除贡献，允许回退（默认原则 3）。
4. **成就回退**：成就进度按未删除记录重算；**条件不再满足的已解锁成就回锁**（`isUnlocked=false`、清 `unlockedAt`、写 `RELOCKED` 事件）。严格性见待确认 Q4。
5. **植物解锁回退**：解锁条件同样重估（如解锁依赖的 GP/记录数跌破阈值则回锁）；但 PlantSnapshot 历史（图鉴养殖记录）**永久保留**，不随回锁删除。
6. **不追溯**：删除释放的当日额度不会补发给当天曾被封顶的其他记录。
7. 同步语义：墓碑优先——服务端已删除的记录不允许被旧设备编辑复活（D10.5）。

## D7. GP 属于空间还是植物：**属于空间**

1. **唯一真相来源**：`space.totalGp = SUM(records.gpFinal WHERE spaceId AND deletedAt IS NULL)`。植物、阶段、进度条全部从空间 GP 派生。
2. **禁止双头**：v1 的「records 总分」与「plant_states.totalGp」两套分数（R3、`PlantDao.getTotalGp` vs `RecordDao.getTotalGp`）在 v2 中合并；植物表不持有 totalGp 字段。`space.totalGp` 仅作为事务内维护的缓存列存在，任何修复入口（迁移、同步校准、调试）都必须从记录集合全量重算。
3. **共享空间**：所有成员记录的 GP 累入同一空间（PRD 3.3.2）；成员贡献度用 `space_members.contributedGp` 缓存展示，不参与阶段计算、不排名。
4. 成就奖励 GP（PRD「第一滴水 +50GP」等）与「GP=记录推导」不变量冲突，v1 一律改为装饰/皮肤/解锁奖励（待确认 Q2）。

---

## D8. 植物更换与历史养成

1. **换植物 = 换载体**：仅更新该空间的活动植物（space_plants 活跃行切换），空间 GP、阶段、进度不变。新植物从当前阶段对应形态继续展示。
2. **历史存档**：被替换植物写入 `plant_snapshots`（plantType、起止时间、达到的最高阶段、期间 GP、记录数），图鉴「过往养殖记录」从快照读取。
3. **PRD「GP 清零重养 / 营养土迁移」废弃**：两者都以「GP 属于植物」为前提，与 D7 冲突；按默认原则 2 裁决废弃（待确认 Q8 确认产品接受）。
4. 每空间同一时刻至多一棵活动植物（v2 部分唯一索引保证）。
5. 阶段快照事件：`STAGE_UP` / `STAGE_DOWN` / `PLANT_SWITCHED` / `PLANT_RETIRED`，作为画册「生长时间轴页」与阶段升级弹窗的数据源（M3）。
6. 共享空间换植物：v1 单机不涉及；服务端版本由创建者/投票规则决定（M5，本 ADR 不冻结）。

## D9. 植物和成就的解锁条件

### 9.1 统一条件类型枚举（默认原则 9）

```
conditionType ∈ {
  DEFAULT,                 // 无条件（默认解锁）
  TOTAL_GP,                // 空间累计 GP（仅个人空间口径）
  STREAK_DAYS,             // 连续记录天数
  RECORD_COUNT,            // 累计记录条数
  RECORD_DAY_COUNT,        // 累计记录日数（去重自然日）
  DISTINCT_LOCATION_COUNT, // 不同地点数（地点名去重）
  PHOTO_COUNT,             // 照片张数（非含照片记录数，修复 R7）
  MUSIC_SONG_COUNT,        // 不同歌曲数（title+artist 去重）
  SHARE_COUNT,             // 外部分享次数
  SHARED_SPACE_EVENT,      // 参数化：INVITE_CO_PLANT / COUPLE_SPACE_JOINED / RESONANCE_7DAYS

}
```

每个定义 = `conditionType + conditionParam(+conditionSubParam)`，由 `AchievementEvaluator` 统一求值；**禁止再出现「全部按 GP」的隐式逻辑**（修复 R8）。

## D10. 离线同步与数据冲突策略

1. **本地优先**：所有写操作先在本地 Room 事务成功并立即反映 UI；网络同步走 Outbox + WorkManager（M4 落地，schema 本轮预留 `outbox_events` 表）。
2. **身份**：每实体 `localId`（自增、永不变）+ `serverId`（服务端分配、一次写入、唯一索引）。同步状态机：`SYNCED / SYNC_PENDING / DELETE_PENDING(墓碑) / CONFLICT`；`version` 单调递增，本地修改即 +1。
3. **权威**：客户端 GP/成就乐观计算（D1）；服务端回包后以服务端 `gpFinal`/进度**校准覆盖**，差异写审计事件（架构方案 Z4-06）。
4. **冲突默认 LWW**：记录类编辑仅作者本人可发起（D11），冲突面收敛为「同作者多设备」；按 `(version, updatedAt)` 最后写入胜出。检测到双方版本分叉（本地 SYNC_PENDING 且服务端 version 更高）时标记 CONFLICT，由用户在 UI 选择保留版本（M4-03）；自动策略默认本地让位。
5. **删除优先**：墓碑的 `deletedAt` 晚于任何编辑的 `updatedAt` → 保持删除；**禁止复活已删除记录**（Z4-05）。
6. **幂等**：Outbox 事件以 `(entityType, localId, operation, version)` 幂等；合种共振以 (spaceId, occurredDate, authorId) 幂等（D1.4）。
7. **首次云端合并**：本地已有数据 + 首次登录 → 用户显式选择合并/仅云端/取消，危险操作二次确认（M4-03）。

## D11. 共享空间成员的编辑、删除和退出权限

| 角色 | 记录（自己的） | 记录（他人的） | 成员管理 | 植物 | 空间设置 |
|---|---|---|---|---|---|
| OWNER 创建者 | 编辑/删除 | 只读+点赞评论 | 邀请/移除/转让 | 选择/更换 | 全部 |
| ADMIN 管理员 | 编辑/删除 | 只读+点赞评论 | 邀请/移除（不能动 OWNER） | — | 部分 |
| MEMBER 成员 | 编辑/删除 | 只读+点赞评论 | — | — | — |

1. **只有作者可以编辑或删除自己的记录**（默认原则 6）；OWNER/ADMIN 不得改删他人内容（PRD 3.3.3、迭代计划 3.7）。
2. **可见性**：非成员不可读；成员退出后立即失去读取权（服务端下发空间数据时按当前成员过滤，Z5-06）。
3. **退出空间**：作者本人的记录可选择「带走」（复制到个人空间：重算进入个人空间 GP，原空间 totalGp 扣减并级联重算）或「留下」（保留在共享空间，仅作者标记移除）；合种植物与快照留在空间（PRD 3.3.3）。
4. **贡献度**：`space_members.contributedGp` 仅作温和展示，不排名不竞争（PRD 3.3.2）。
5. 服务端为权限最终权威；v1 离线单机只有默认个人空间（OWNER=本机用户）。

## D12. Demo 数据与正式数据隔离

1. **正式包（release 与正式 debug）首启不插入任何 Demo 记录**（默认原则 7）：首启只创建默认个人空间、植物目录、成就定义——这些是**产品内容**（类似内置词典），不是 Demo 数据。
2. Demo 记录仅允许存在于：`src/debug/` 的 Debug fixture（`BuildConfig.DEBUG` 且显式开关）、 instrumentation test 种子、onboarding 静态示例卡（资源文件渲染，不入库）。
3. 现有 `XiaoQueXingApp.initializeData()` 的 5 条 Demo 记录（R3）在 Z1-07 移除；其 116 GP 与植物 0 分的既有不一致由 v1→v2 迁移统一裁决为「以记录集合为准」（room-v2-schema §5 步骤 5e）。
4. 画册 Demo 页面内容同理：不允许以硬编码数据冒充功能完成（迭代计划 2.3）。
